# HK-001 Golden Path Runtime Design

**Status:** Approved for implementation

**Date:** 2026-07-16

**Scope:** Hong Kong Buddy launch contract, pilot access, provider readiness, and Flash Launch smoke integration

## Goal

Make Hong Kong Buddy a production-safe, reproducible Flash Launch workload for the existing Azure pilot provider profile:

- Azure OpenAI for tutor and correction generation;
- Azure Translator for visit translation;
- MiniMax for Cantonese text-to-speech;
- Azure Speech for speech recognition.

The application must expose truthful process liveness, exact configuration readiness, and one authenticated real-provider smoke. It must also protect every user-facing API behind a shared pilot access code without storing that code in the browser or application metadata.

## Launch Contract

Flash Launch treats the repository root as the application root.

The canonical runtime contract is:

```text
root directory: .
Node runtime: 22
package manager: pinned npm
install: npm ci
build: npm run build
start: npm start
liveness: /api/live
readiness: /api/ready
provider smoke: /api/internal/provider-smoke
```

The root owns the only lockfile used for launch. Root scripts orchestrate backend installation/build checks, frontend build, frontend-to-backend public synchronization, regression tests, and server startup. A clean clone using only the declared root commands must produce the same runnable artifact as local development.

Generated frontend output is synchronized into `backend/public`. A check command fails when the committed or built public assets drift from the frontend output.

## Runtime Topology

The production Cloud Run service uses:

- `minInstances=0`;
- `maxInstances=1` for this pilot tranche;
- one Node/Express process serving both API routes and the static frontend;
- in-memory pilot login throttles, pilot sessions encoded in signed cookies, and bounded in-memory provider quotas.

The exact production provider selectors are:

```text
LLM_PROVIDER=azure-openai
TTS_PROVIDER=minimax
ASR_PROVIDER=azure
ASR_FALLBACK_PROVIDER=
VISIT_TRANSLATION_PROVIDER=azure
```

Production readiness rejects missing, different, mock, or fallback selector values. The visit translation selector is an explicit application contract added by this work so credentials alone cannot make readiness pass while user traffic follows another translation path.

The single-instance limit is a declared compatibility constraint, not an assertion of horizontal scalability. Durable conversations, distributed rate limiting, and multi-instance session state are deferred.

## Shared Pilot Access

### Secret material

Production requires:

- `PILOT_ACCESS_CODE_HASH`: a versioned, salted password hash generated by a repository script that accepts the code through stdin;
- `PILOT_SESSION_SECRET`: high-entropy key material used to authenticate session cookies.

The raw pilot code is never placed in source, a command-line argument, client storage, logs, metadata, tests, or deployment fingerprints. Production startup or readiness fails closed if either secret is missing or malformed. Auth may be disabled only in an explicit test environment.

### Session cookie

Successful login issues a stateless HMAC-authenticated session cookie with issue and expiry timestamps.

Production cookie attributes are:

```text
Name: __Host-hkbuddy_pilot
HttpOnly
Secure
SameSite=Strict
Path=/
Max-Age=8h
No Domain attribute
```

Development uses a visibly different cookie name and does not weaken the production cookie contract. Cookie verification uses constant-time signature comparison and rejects malformed, expired, future-issued, or incorrectly versioned payloads.

### Access endpoints

The public pilot access endpoints are:

- `POST /api/pilot/login`
- `GET /api/pilot/status`
- `POST /api/pilot/logout`

Login accepts only the access code, uses a 4 KB body limit, performs constant-time hash verification, rotates the session value on success, and returns no secret-derived material. Logout clears the cookie with matching attributes.

### Route boundary

Anonymous access is limited to:

- `GET /api/live`;
- `GET /api/ready`;
- pilot login, status, and logout;
- `POST /api/internal/provider-smoke`, authenticated by Flash smoke credentials rather than the pilot session.

Every other `/api` route, including `/api/speech-token`, requires a valid pilot session. Static assets and the application shell remain accessible so the browser can render the access dialog.

## Request Pipeline

Middleware order is security-significant:

```text
trusted proxy and request metadata
  -> exact-origin mutation check
  -> login throttle
  -> anonymous route dispatch
  -> pilot-session authentication
  -> weighted provider quota
  -> route-specific body parser and validation
  -> provider call
```

Production accepts mutating browser requests only when `Origin` exactly matches `PUBLIC_APP_ORIGIN`, an HTTPS origin injected from Flash's Cloud Run `status.uri` readback. The application never derives this origin from `Host`, `X-Forwarded-Host`, or `X-Forwarded-Proto`. There are no hard-coded Azure, localhost, or GitHub origins in the production allowlist. Missing or foreign origins fail closed where the route is browser-mutating; Cloud Run internal smoke uses its separate machine-authenticated boundary.

Express trusts exactly one proxy hop in Cloud Run production (`trust proxy = 1`). Rate-limit identity is the nearest untrusted address from the right of the forwarded chain after that one trusted hop; attacker-supplied addresses farther left are ignored. Production readiness rejects a boolean trust-all setting or any other hop count. `X-Forwarded-Host` is ignored, and spoofed host, forwarded-protocol, or left-side forwarded-for values cannot change the canonical origin or quota key. Non-Cloud-Run development defaults to no trusted proxy unless an explicit test fixture configures the parser.

Request body limits are route-specific:

- pilot login: 4 KB;
- ordinary JSON routes: 256 KB;
- speech audio compatibility route: 10 MB request ceiling plus encoded-size, decoded-size, duration where available, and MIME validation.

Malformed content types, oversized encoded audio, oversized decoded audio, and unsupported audio types are rejected before a provider call.

## Abuse Budgets

The pilot uses bounded token buckets with TTL eviction and a maximum number of entries. Unknown or attacker-controlled identifiers cannot grow maps without bound.

Budgets are:

- login: 5 attempts per IP per 15 minutes;
- speech token: 3 requests per session/IP per 10 minutes;
- provider usage: 60 weighted units per session per 10 minutes and 100 per IP per 10 minutes.

Weights are:

- speech recognition: 3;
- visit translation: 2;
- correction, tutor chat, speech-to-text compatibility, speech token, translation helpers, and TTS voice discovery: 1.

Quota responses use a stable error code and bounded `Retry-After`. They do not disclose whether a session, IP, or upstream account was the limiting key.

## Readiness Model

### Process liveness

`GET /api/live` answers only whether the process can serve requests. It returns 200 without reading provider secrets, contacting a provider, or exposing configuration detail.

### Configuration readiness

`GET /api/ready` validates the exact Golden Path configuration and returns 200 or 503. It checks, without making paid calls:

- Azure OpenAI endpoint, deployment/model selection, API version, and credential presence;
- Azure Speech region/endpoint and credential presence;
- MiniMax endpoint/model/voice selection and credential presence;
- Azure Translator endpoint/region and credential presence;
- pilot access hash and session secret validity;
- Flash smoke token and deployment-id binding configuration;
- production trust-proxy and origin prerequisites.

Readiness also proves the exact production selectors: Azure OpenAI LLM, MiniMax TTS, Azure ASR with no fallback, and direct Azure visit translation. Merely having credentials for all four providers is insufficient.

The anonymous response is strictly aggregate and allowlisted: HTTP 200 with `{"status":"ready"}` or HTTP 503 with `{"status":"not_ready","code":"CONFIG_NOT_READY"}`. It never returns component names, endpoints, deployment names, regions, secret lengths, key prefixes, selector values, environment variable values, or exception bodies. Component-level diagnostics are available only from the pilot-authenticated `/api/health` response and redacted controlled logs.

The existing authenticated `/api/health` becomes a strict logical AND of required application capabilities rather than an optimistic liveness alias.

## Flash Provider Smoke

### Authentication and idempotency

`POST /api/internal/provider-smoke` requires all of:

- an `Authorization` bearer token whose Google signature, issuer, expiry, service-URI audience, and caller identity the application verifies; Cloud Run IAM independently enforces invocation when the service is private;
- `X-Flash-Smoke-Token` matching the deployment-scoped secret in constant time;
- `X-Flash-Deployment-Id` matching the configured deployment id;
- a valid `Idempotency-Key` identifying the smoke attempt.

The cross-repository environment contract is exact:

- `FLASH_LAUNCH_SMOKE_TOKEN` comes from a Flash-created Secret Manager secret pinned to the numeric version for this deployment;
- `FLASH_LAUNCH_DEPLOYMENT_ID` is the immutable deployment id and must equal the request header;
- `FLASH_LAUNCH_SMOKE_CALLER` is the exact Flash worker service-account identity accepted from the verified Google token;
- `PUBLIC_APP_ORIGIN` is the provider-read canonical service origin, never a request-derived value.

The token and deployment id are candidate-specific; caller and origin are provider-read platform configuration. Missing or malformed values make `/api/ready` return the aggregate 503 response. The application does not accept aliases or a `latest` secret-version convention.

The endpoint never accepts the pilot session cookie as machine authentication. It rejects missing, malformed, reused-with-conflicting-input, or expired attempt identifiers.

The application stores only a bounded in-memory attempt result cache because Flash owns the durable attempt record and the pilot is constrained to one instance. A duplicate completed attempt returns the same aggregate result without repeating provider calls. An attempt that may have crossed a paid-call boundary but lacks a complete result returns an inconclusive state rather than silently repeating work.

### Provider sequence

Each provider is called exactly once with minimal synthetic input and no automatic retry or fallback:

1. Azure OpenAI receives a minimal deterministic Cantonese tutor prompt and must return a non-empty bounded text result.
2. Azure Translator is called directly with a short synthetic phrase; no `Promise.any`, secondary translator, or mock path is allowed.
3. MiniMax TTS synthesizes a short Cantonese phrase; the response must have an allowed audio MIME type and bounded non-zero size.
4. Azure Speech recognizes that synthetic MiniMax audio; the response must contain a non-empty transcript.

Using the MiniMax output as the Azure Speech input verifies the actual TTS-to-ASR integration without shipping a repository audio fixture. Provider response content and audio are discarded after validation.

### Smoke response and logging

The response includes only:

- overall `passed`, `failed`, or `inconclusive` status;
- provider identifier;
- provider status;
- latency;
- bounded usage counters such as input/output characters or audio bytes/duration;
- stable redacted error code.

Prompts, completions, translated text, transcripts, audio, access code, cookies, tokens, upstream response bodies, and raw provider errors are never logged or persisted.

## Browser Access Experience

The frontend checks `GET /api/pilot/status` during application initialization with credentials enabled. An unauthenticated response opens a blocking pilot access dialog before provider-backed work can be performed.

The dialog:

- contains one access-code field;
- submits directly to the login endpoint;
- never writes the code to local storage, session storage, IndexedDB, URL state, analytics, or application logs;
- clears the field after success and on close/reset;
- presents generic invalid-code and throttled states.

All application fetches send same-origin credentials. When an authenticated request receives 401, clients join one shared reauthentication promise, show the dialog once, and retry the original request at most once after successful login. Independent recursive retries are forbidden.

Frontend source is changed first and then synchronized to `backend/public`; generated assets are not hand-edited.

## Graceful Shutdown

On `SIGTERM` or `SIGINT`, the process:

1. stops accepting new HTTP requests;
2. waits for active requests for a bounded drain period;
3. closes the server and exits successfully when drained;
4. exits after the deadline without printing request or provider bodies.

Readiness changes to unavailable during drain. No new provider smoke may start after shutdown begins.

## Error and Privacy Contract

Application errors are mapped to stable public codes. Logs contain request id, route family, status, latency, provider identifier where relevant, and redacted error classification.

The following are prohibited in logs and client-visible diagnostics:

- raw user utterances, prompts, correction input, or translated content;
- upstream response bodies or SDK exception serialization;
- audio or base64 prefixes;
- session cookies, Flash smoke tokens, provider keys, and access codes;
- exact readiness configuration values.

Operational metrics count requests, outcomes, latency buckets, and weighted quota consumption without content payloads.

## Verification Strategy

Implementation proceeds in test-driven slices. Required automated coverage includes:

- root `npm ci`, build, test, start, and frontend synchronization from a clean clone;
- only the root lockfile participates in the launch contract;
- production startup/readiness fails closed when pilot secrets are absent;
- correct login sets the exact production cookie attributes;
- bad, expired, tampered, or future-issued sessions fail;
- every provider-backed API, including speech-token, rejects anonymous use;
- liveness stays independent of provider configuration;
- readiness is 503 for each individually missing required provider or access setting;
- readiness responses contain no secret or endpoint details;
- credentials with a wrong provider selector, mock provider, or ASR fallback still produce not-ready;
- foreign-origin mutation requests are 403;
- spoofed `Host`, `X-Forwarded-Host`, `X-Forwarded-Proto`, and left-side `X-Forwarded-For` values cannot alter origin enforcement or the rate-limit identity;
- route-specific body limits reject oversized data before provider invocation;
- login and weighted provider budgets enforce limits and evict stale entries;
- smoke rejects invalid Google/Flash/deployment/idempotency boundaries;
- duplicate completed smoke attempts do not call providers again;
- each smoke provider is called exactly once and fallback/mock paths are impossible;
- MiniMax audio is the exact payload validated by Azure Speech;
- response and captured logs contain no synthetic content, audio, key, token, or upstream body;
- one 401 across concurrent browser calls creates one access dialog and one reauthentication flow;
- successful reauthentication retries each request no more than once;
- `SIGTERM` stops readiness and drains within the configured deadline.

End-to-end release verification runs the Flash candidate with its applicable new-service or existing-service access boundary and real Azure OpenAI, Azure Translator, MiniMax, and Azure Speech credentials; completes the provider smoke; promotes only after success; and exercises login, practice, translation, TTS, ASR, throttling, logout, and re-login in a browser.

## Delivery Order

Work lands on `agent/hk001-golden-path` in small commits, pushed after each verified slice:

1. Reproducible root launch contract.
2. Shared pilot access and fail-closed route boundary.
3. Same-origin enforcement, body limits, and bounded provider budgets.
4. Exact Azure pilot readiness surfaces.
5. Idempotent authenticated four-provider smoke.
6. Pilot access UI, shared reauthentication, redacted logging, and graceful shutdown.
7. Flash Launch integration evidence for `hk-001`.

Each commit includes the tests and documentation needed to establish its behavior. The branch remains unmerged until the Flash candidate/promotion path and real provider smoke pass.

## Non-Goals

- Per-user accounts, invitations, billing, or role-based access control.
- Durable conversation history or distributed session storage.
- Horizontal scaling beyond the declared single-instance pilot.
- Provider fallback during launch certification.
- Replacing Azure OpenAI, Azure Speech, Azure Translator, or MiniMax.
- Removing the existing Azure-hosted deployment.
- Custom domains, marketing pages, or pricing work.
- Automatic production deployment on source push.
